## B4 — actual worker command is not verified in the direct-parent branch

Priority: blocking for the requested exact-worker-CLI contract. Locations: `D3/reward_input_integrity.py:90-120`, `D3/reward_smoke_small.py:146-148`, `D3/visual_model_smoke_small.py:215`, and receipt acceptance at helper lines 123-128.

Both workers construct `expected_command` by prefixing `sys.argv` with the intended isolated interpreter and `-B -X utf8`. The helper compares that reconstructed suffix with the same `sys.argv`. It never reads `current.cmdline()`. For the direct-parent branch, therefore, the check does not establish the actual interpreter options of the worker. The returned `worker_command` is the supplied reconstruction, not an observed OS command. The single-launcher branch does independently read and compare the intervening launcher's executable and command; that does not close the direct-parent omission.

A bounded mock used the accepted logical parent PID, creation time, same entry and `run` action, but supplied a current-worker OS command with `-B` omitted. It was accepted and returned a receipt asserting `-B`. This is a source-level counterexample, not a real launch or observed runtime failure. The fixed parent source normally constructs the intended flags; the finding is that the worker validation and evidence claim do not enforce the specified rejection property.

There is a related canonical-argument gap in the visual worker: its expected full command is derived from `sys.argv`, not independently reconstructed from parsed method/plan/hash/output values. An equivalent duplicated `--method` option was accepted by the mocked helper. Such a duplicate is not necessarily a scientific change, but it is a changed command under the requested exact-command rule. The reward worker is stronger here: it compares frozen remaining arguments with `command(...)[3:]` and compares its reconstructed command with the parent's pre-launch `*_COMMAND.json`. That reward artifact comparison still cannot detect omitted actual interpreter flags because those flags are synthetically inserted. The parent receipt validator checks PID/creation-time binding and the verification flag, not the receipt command against its own Popen command.

Closure requires independently comparing the actual current-worker OS command with the declared canonical worker command on both admitted parent paths, and constructing that canonical command from independently checked worker arguments rather than using `sys.argv` as its own oracle. Keep the allowed Windows venv redirection distinction: the native executable can be the base Python executable while the declared command's argv[0] and `sys.executable` represent the isolated environment. Do not demand native-executable equality without accounting for that documented redirection. This review does not implement a repair or approve a subsequent version.

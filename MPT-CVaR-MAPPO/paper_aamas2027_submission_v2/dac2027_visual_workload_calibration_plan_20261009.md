# QLA-MAPPO：实际视觉工作负载与硬件校准实验方案

日期：2026-10-09。用途：为面向 DAC 的论文补充“真实推理测量 → 环境校准 → 多智能体协调评估”的证据链。

本文是待执行的实验设计，不是已有实验结果。本文生成时未下载图片或模型、未启动测量或训练，也未修改正文、附录及算法代码。以下样本量、阈值和实验矩阵均为建议协议，须在正式测试前冻结。

## 1. 先给结论：推荐怎么做

最小而完整的方案是：**Imagenette 原尺寸图片 + ImageNet 预训练 ResNet-18 + 两种 CPU 资源配置 + 实测校准的队列模拟 + 配对多种子策略比较**。

不必训练视觉模型，不必搭建 35 台实体服务器，也不必下载完整 ImageNet。需要训练的可能是校准环境中的卸载策略，而不是 ResNet-18。

三个量必须区分：

| 量 | 怎样得到 | 它表示什么 |
| --- | --- | --- |
| 上传大小 `payload_bytes` | 读取实际发送的 JPEG 字节串，取 `len(payload)` | 网络传输量 |
| 模型输入形状 | 记录预处理后的张量，例如 `1×3×224×224` | 推理计算的输入规格；不是上传量 |
| 服务时间 `service_ms` | 在指定资源配置下，对真实推理流水线逐请求计时 | 服务器为该请求占用执行资源的时间；不含排队 |

**数据集提供图片，不提供你的 CPU/GPU 上的服务时间。服务时间分布必须通过本地测量得到，不能由图片大小、模型参数量或 FLOPs 直接替代。**

核心研究问题：

> 当上传量来自真实图片、服务时间来自真实推理测量，而非统一常数时，QLA-MAPPO 的联合卸载协调是否仍能改善平均时延和尾部时延，并抑制集中需求及队列冲击？

这里的“真实”分别指图片内容和推理执行；网络及多服务器交互若仍由模拟器产生，论文必须称为“实测校准的模拟”，不能称为校园实体部署。

### 2.2 视觉模型：预训练 ResNet-18

使用 TorchVision 的 `resnet18` 和明确的权重版本 `ResNet18_Weights.IMAGENET1K_V1`，不要只写会随软件版本变化的 `DEFAULT`。其官方预处理将图片缩放并中心裁剪为 224×224，再进行归一化。[官方模型与预处理说明](https://docs.pytorch.org/vision/stable/models/generated/torchvision.models.resnet18.html)

- [官方预训练权重文件](https://download.pytorch.org/models/resnet18-f37072fd.pth)
- [权重 URL 与版本定义的官方源码](https://docs.pytorch.org/vision/stable/_modules/torchvision/models/resnet.html)
- [ResNet 原始论文](https://arxiv.org/abs/1512.03385)

首次调用以下代码可能联网下载权重；本方案只给出用法，未执行下载：

```python
from torchvision.models import resnet18, ResNet18_Weights

weights = ResNet18_Weights.IMAGENET1K_V1
model = resnet18(weights=weights).eval()
preprocess = weights.transforms()
```

固定 `batch_size=1`、FP32、模型常驻内存、`eval()` 和 `torch.inference_mode()`。不使用动态批处理、量化或编译优化作为主实验的一部分，避免同时改变任务服务语义；这些可以另做系统优化实验。

注意两点：

1. Imagenette 十类不等于“十个校园建筑”，ResNet-18 的 ImageNet 分类头也不是建筑身份识别器。主实验验证的是**真实视觉分类服务负载下的卸载协调**。
2. Imagenette 来源于 ImageNet，可能与预训练数据重叠。这里不提出新的识别准确率或视觉泛化贡献；准确率/预测一致性仅作流水线健康检查。不要把其图片划分包装成视觉模型独立泛化测试。

若做分类健康检查，应把类别目录的 WordNet ID 映射到模型的 ImageNet 类别索引，不能将十类文件夹顺序直接当作 1000 类输出索引。保留映射文件及来源。

## 3. 请求流水线与“上传大小”如何计算

主实验统一采用“客户端发送原 JPEG → 服务器解码 → 官方预处理 → ResNet-18 推理 → 返回类别和分数”。各策略使用相同模型、图片编码和输入质量。

### 3.1 四种容易混淆的大小

| 名称 | 定义 | 是否用于主上传模型 |
| --- | --- | --- |
| 文件字节数 | 原 JPEG 文件长度 | 原样发送时可以 |
| 应用层载荷字节数 | 实际发送请求体的长度 | **推荐采用** |
| 链路传输字节数 | 请求体加协议、TLS、重传等开销 | 只有抓包/链路测量时才报告为实测值 |
| 解码张量大小 | 像素张量的内存量 | 不是发送 JPEG 时的上传大小 |

计算示例：

```python
from pathlib import Path
from PIL import Image
from io import BytesIO

path = Path("一张图片.JPEG")
payload = path.read_bytes()
payload_bytes = len(payload)
with Image.open(BytesIO(payload)) as image:
    width, height = image.size

payload_mb = payload_bytes / 1_000_000      # 十进制 MB
payload_mib = payload_bytes / (1024 ** 2) # 二进制 MiB
```

例如，224×224×3 的 FP32 张量占 `602,112` 字节，uint8 像素数组占 `150,528` 字节；二者都不等于对应 JPEG 的压缩字节数。模型输入固定为 224×224，也不代表原 JPEG 大小相同。

若客户端先缩图或重压缩，应先生成实际发送的编码结果，再取其字节长度，同时固定分辨率、JPEG 质量和编码库版本；不要继续使用原文件大小。Base64 请求体通常比二进制更大，不建议主实验无必要地采用。

### 3.2 从字节数到通信时间

若有效传输速率为 `R` bit/s：

\[
T_k^{\rm upload}=\frac{8b_k}{R_{ij}}.
\]

其中 `b_k` 为请求体字节数。若速率单位为 MB/s，需先确认 MB 为十进制还是二进制。

假设某载荷为 200,000 字节、有效速率为 20 Mbit/s，则载荷传输项是 0.08 s。**这只是单位换算示例，不是你的数据或硬件测量结果**；它不含握手、排队、竞争和重传。

现有环境的 `_throughput_mb_s()` 使用 `bits_s / 8 / 1024 / 1024`，实际上是二进制 MiB/s。接入字节数时，相应数据量应是 `b_k / 1024**2`；若改成十进制 MB/s，必须同时改数据量，不能只改一端。

两种证据层级不要混写：

- **最小主实验**：图片字节数和推理服务时间实测，距离相关网络速率仍按模型计算。称为“实测工作负载/计算服务校准的模拟”。
- **增强实验**：用客户端和推理服务实际传输图片，测上传与响应时间；若仅 localhost 或局域网限速，也要明确，不是校园无线网络实测。

## 4. 服务时间必须怎样测

### 4.1 时间边界

建议记录以下事件；单机差值采用单调高精度时钟，不用系统日期时间作短时计时：

| 时间戳 | 含义 |
| --- | --- |
| `t_client_start` | 客户端请求开始；仅真实请求实验使用 |
| `t_received` | 服务器收完请求体 |
| `t_enqueued` | 请求进入服务器队列 |
| `t_worker_start` | 工作线程/进程开始处理该请求 |
| `t_decode_end` | 解码和 RGB 转换完成 |
| `t_preprocess_end` | 输入张量准备完成，包括必要设备传输 |
| `t_infer_end` | 推理结果确已计算完成 |
| `t_result_ready` | 类别/分数提取与结果对象生成完成 |
| `t_client_end` | 客户端收到结果；仅真实请求实验使用 |

定义：

\[
S_k=t_{\rm result\ ready}-t_{\rm worker\ start},\qquad
W_k=t_{\rm worker\ start}-t_{\rm enqueued}.
\]

`S` 包含解码、预处理、推理和轻量后处理，不含上传、排队和 QLA 控制器计算。如果实际服务包括 JSON 序列化等额外步骤，要加入边界并记录，不能只测网络算子后称为整个服务时间。

真实端到端时间用同一客户端时钟的 `t_client_end-t_client_start`。跨设备时不要直接相减未同步的客户端和服务器绝对时钟；服务器阶段时长在服务器自身时钟内计算。

### 4.2 计时条件

1. 固定 `batch=1`、FP32、模型和权重、输入预处理；关闭训练行为和梯度。
2. 模型加载一次并常驻，至少预热 200 次，然后正式测量；预热不进入统计。
3. JPEG 字节可在计时前读入内存，**图像解码仍应在服务计时内**。这样不把本地磁盘读文件误当作服务器处理上传请求。
4. 每次正式处理一张图片；不要把一整批总时间除以图片数当作单请求服务分布。
5. 保存逐请求原始记录，日志写盘放在计时区间之外。
6. CPU 使用 `time.perf_counter_ns()`；GPU 必须等待设备完成，不能只测异步提交时间。
7. 固定并记录 CPU 线程数、进程亲和性、电源模式、软件版本；关闭与实验无关的重任务。
8. 同一测量块内不要运行强化学习训练或多个互相争抢的模型进程。若研究并发工作进程，其服务配置必须单独实测，不能套用独占测量。

官方依据：[CPU 算子线程设置](https://docs.pytorch.org/docs/2.14/generated/torch.set_num_threads.html)、[interop 线程设置](https://docs.pytorch.org/docs/2.14/generated/torch.set_num_interop_threads.html)、[GPU 同步接口](https://docs.pytorch.org/docs/2.14/generated/torch.cuda.synchronize.html)、[PyTorch 基准测量注意事项](https://docs.pytorch.org/docs/2.14/benchmark_utils.html)。链接指向核对时可读的官方文档；实验不要求升级到该文档版本，应冻结实际使用的软件版本。

### 4.3 核心计时示例

以下是测量核心，不是完整采样与日志脚本；完整实现还需加入图片清单、会话分块、预热、错误处理和 CSV 保存。本次没有执行它。

```python
import time
from io import BytesIO
from PIL import Image
import torch
from torchvision.models import resnet18, ResNet18_Weights

# 每种资源配置使用独立新进程；必须在模型执行前设置。
torch.set_num_threads(1)        # 配置 B 时改为 4
torch.set_num_interop_threads(1)
device = torch.device("cpu")   # 未确认 GPU 时，不假定存在 GPU
weights = ResNet18_Weights.IMAGENET1K_V1
model = resnet18(weights=weights).eval().to(device)
preprocess = weights.transforms()

def sync():
    if device.type == "cuda":
        torch.cuda.synchronize(device)

@torch.inference_mode()
def measure_one(payload: bytes):
    sync()
    t0 = time.perf_counter_ns()
    with Image.open(BytesIO(payload)) as source:
        image = source.convert("RGB")
    t1 = time.perf_counter_ns()

    x = preprocess(image).unsqueeze(0).to(device)
    sync()                    # 输入拷贝若为异步，先确认完成
    t2 = time.perf_counter_ns()

    logits = model(x)
    sync()                    # 不能把 GPU 提交时间当作完成时间
    t3 = time.perf_counter_ns()

    predicted_class = logits.argmax(dim=1).item()
    result = {"class_index": predicted_class}
    t4 = time.perf_counter_ns()
    return {
        "payload_bytes": len(payload),
        "decode_ms": (t1 - t0) / 1e6,
        "preprocess_ms": (t2 - t1) / 1e6,
        "infer_ms": (t3 - t2) / 1e6,
        "postprocess_ms": (t4 - t3) / 1e6,
        "service_ms": (t4 - t0) / 1e6,
        "predicted_class": result["class_index"],
    }
```

如果最终 API 返回分数、序列化 JSON，则计时实现须同步加入这些步骤。为了降低插入计时点的扰动，可另测不插入中间时间戳的全流水线总时间，验证分阶段版本没有显著改变服务时间。

固定形状的 ResNet 前向计算量基本不随 JPEG 字节数变化。图片间差异可能主要来自解码、缩放及系统抖动，所以必须同时报告分阶段时间，不预设“文件越大，推理一定越慢”。

## 5. 至少两种资源条件：现有单机就能开始

论文记录的机器是 AMD Ryzen 7 9700X / Windows 11。先核实当前机器与软件版本，不假定已有第二台边缘设备或 GPU。

### 5.1 推荐最小资源配置

| 配置 | 固定条件 | 可支持的解释 |
| --- | --- | --- |
| A：CPU-1T | 单服务进程，算子线程 1，interop 线程 1，FP32、batch 1 | 受限 CPU 资源配置 |
| B：CPU-4T | 同一 CPU，算子线程 4，interop 线程 1，其余相同 | 较多 CPU 执行资源配置 |

二者是**同一硬件上的两种资源配置**，不是两种实体设备。不要预设 4T 一定比 1T 快或恰好快四倍；以实测结果为准。PyTorch 线程设置需要在执行前完成，interop 设置只能在相应并行工作开始前设置，因此每个测量块应启动独立进程。[官方限制](https://docs.pytorch.org/docs/2.14/generated/torch.set_num_interop_threads.html)

1T 进程限制在一个物理核心对应的可用执行资源上；4T 使用预先指定的四个物理核心。先查 CPU 拓扑，不把连续逻辑 CPU 编号直接当作四个独立物理核心。两种配置分别测量，记录核心集合和后台状态。

### 5.2 可选增强配置

- 有第二台机器：同模型同精度，比较桌面 CPU 与边缘设备；准确记录设备名称，不仅写“slow/fast server”。
- 有 GPU：加入 CPU/GPU 服务配置，但设备传输和同步应包含在服务边界内；不能把 CPU-FP32 与 GPU-INT8 的差异全归因于硬件。
- 背景负载实验：固定推理线程配置，比较无背景负载和受控背景负载。记录负载生成方式、CPU 实际利用率及时间序列；不要用未知后台任务制造尾时延。

最小方案只要求 A/B。额外设备、背景负载、第二模型和实机集群不应成为启动实验的前置条件。

## 6. 图片、测量会话与数据划分

### 6.1 分开四个用途

以下是建议采样量，下载清点后确认每类图片足够；不足时在看策略结果前等比例调整并冻结。

| 图片池 | 建议数量 | 用途 | 可否用于最终结论 |
| --- | --- | --- | --- |
| 预热/预实验 | 另取 50–100 张 | 检查代码、测量量级、决定时间尺度 | 不计入正式指标 |
| 校准/策略训练池 | 2,000 张，来自官方 train，按十类分层 | 建模输入量与服务分布，生成策略训练负载 | 不能当作独立测试 |
| 校准验证/策略验证池 | 500 张，来自 train 的不重叠部分 | 检查校准误差、冻结参数和策略选择规则 | 不用于最终效果报告 |
| 最终测试池 | 1,000 张，来自官方 val，按类分层 | 测量保留样本，形成最终请求日程 | 可以 |

这些划分针对卸载系统实验；视觉模型本身不训练。图片 ID 和 SHA-256 不重叠；统计重复或近重复图片并说明处理方式。给采样程序固定随机种子，例如 `20261009`。

### 6.2 会话与测量量

每个会话包含两个资源配置的测量块；两者使用相同图片清单和顺序。建议：

- 校准：5 个独立启动的会话，每个配置每会话测 2,000 张，共 **10,000 条/配置**。
- 验证：3 个新会话，每个配置测 500 张，共 1,500 条/配置。
- 测试：冻结校准参数后，5 个保留会话，每个配置测 1,000 张，共 5,000 条/配置。
- 总计：33,000 条正式服务计时，不含预热；是规划数量，不是当前已有数据。

每个会话采用独立进程启动与预热，分散到不同时间段；每会话按小块交替 A/B，首块顺序随机且跨会话反平衡，避免所有 A 都在机器冷时测、所有 B 都在机器热时测。每个新进程都需要完成预热；持续监测温度、频率和负载。

同一图片多次运行不是多个独立硬件样本。服务统计的不确定性按“会话 → 图片”分层或按会话块重采样；报告会话数量。单机重复启动也不等于多设备泛化证据。

总时间先由预实验中服务时间估计：`测量次数×平均服务时间 + 预热 + 进程/日志开销`。不要在未测量前承诺完成时间。

### 6.3 原始记录字段

```text
session_id, block_id, run_order, profile_id, model_id, weights_sha256,
image_id, image_sha256, image_split, class_id, width, height,
payload_bytes, decode_ms, preprocess_ms, infer_ms, postprocess_ms,
service_ms, predicted_class, cpu_threads, cpu_affinity, device,
software_versions, measurement_timestamp, error_status
```

错误、解码失败和异常慢请求都保留记录。只有可核实的测量程序故障可按冻结规则剔除；不得按时延分位数剪掉慢样本后再报告 P99。冷启动另列，不与稳态服务混合。

## 7. 服务时间分布怎样计算与建模

### 7.1 先描述，不先假定指数分布

对每个资源配置分别报告：样本数、会话数、均值、标准差、变异系数、中位数、P90、P95、P99，以及服务时间 ECDF/CCDF。展示总服务和各阶段的比例。

分位数的可复现定义可固定为经验次序统计量：升序样本 `S_(1)≤…≤S_(n)`，`P_p=S_(ceil(pn))`。不要图表使用一种插值方法、正文使用另一种方法却不说明。

可计算：

\[
\widehat F_p(s)=\frac{1}{n_p}\sum_r\mathbf 1\{S_{r,p}\le s\},
\qquad \bar S_p=\frac{1}{n_p}\sum_r S_{r,p}.
\]

**10,000 条/配置大约提供 100 条最慢 1% 观测，但不是 100 条独立设备观测。** 本方案主报 P99，不在样本不足时把 P99.9 当稳定结论。

### 7.2 保留有物理意义的相关性

最简单的校准输入是保留每张图片的字节数和其在 A/B 下的配对测量，不能把上传大小和服务时间各自打乱独立采样。

先检查：

- 总服务差异是否主要来自解码与原图分辨率；
- A/B 的相对速度是否随图片类型或尺寸改变；
- 同一测量会话是否存在共同慢化；
- 服务时间序列是否有短时自相关、升温漂移或后台抖动。

推荐优先使用**配对经验表或按会话的块重放**，而不是仅输入一个平均服务率。若建立条件预测器，只能使用请求时可获得的元数据，如载荷大小、原始分辨率和服务配置；在校准池拟合，在验证池选复杂度并冻结。

最终测试图片的实测时间可以作为执行层的保留真值，但不能用来拟合预测器、调归一化或选择策略 checkpoint。客户端/actor 不得提前看到测试请求实际会发生的硬件抖动。

### 7.3 独立校准验收

将预测/重放分布与保留验证测量对比。预先定义工程容差，例如：均值误差不超过 10%、P95 不超过 15%、P99 不超过 20%。这些是建议的建模验收线，不是通用统计标准；应在正式策略测试前冻结。

若验证失败，增加合理的元数据分层或改用经验表，不通过修改测试负载来“让模型通过”。无论通过与否均存档校准误差。

## 8. 如何接入你现在的模拟器

### 8.1 已核对的代码事实

现有代码已经区分 `task_package_mb`（通信载荷）与 `task_compute_mb`（计算工作量），并不是同一个变量同时表示两者。

目前的主要限制是它们在配置中基本是统一标量，而非逐图片的实测输入；服务按 `task_compute_mb / edge_capacity` 计算。需要补的是**逐任务异质性、实测服务分布与正确单位**，不是将已有两种变量重新合并。

需核对和适配的入口：

| 文件/接口 | 现状 | 校准实验应做的工作 |
| --- | --- | --- |
| `mappo_gp_sf_dsr/config.py` | `task_package_mb`、`task_compute_mb`、时隙和队列上限 | 增加任务清单/服务配置入口；实验配置写明实际覆盖值 |
| `mappo_gp_sf_dsr/env.py: TaskRecord` | 已含载荷、计算量和通信/服务时间 | 关联 `image_id`、逐任务字节数和执行服务要求 |
| `joint_step` / `sequential_step` | 逐任务创建记录，但使用统一大小 | 从同一持久化日程读取逐任务属性 |
| `_transmission_delay_s` | 固定载荷除传输速率 | 输入 `b_k`，保持 MB/MiB 与速率一致 |
| `_serve_and_admit` | 先服务旧队列，再按上传完成顺序整任务接纳 | 保留任务记账与守恒，核对长上传和真实到达时刻 |
| 请求摘要与 `portfolio_stats` | 请求数乘统一工作量 | 改成各用户实际/预测计算工作量的求和，不用 JPEG 字节代表计算需求 |
| `train.py` 的 QL/服务预测 | 多处使用统一 `task_compute_mb` | 使用冻结的可观测服务预测，不读取未来实际服务时间 |
| `delayed_information_baselines.py` 等适配器 | 也有固定服务量假设 | 与主方法同步接入，不只校准 QLA |

以上是待实施点，不代表本次已经改代码。不要直接用历史默认配置代替最终实验配置；所有方法应使用同一校准协议。

### 8.2 两条接入路线，先验收再决定

**路线 A：参考计算工作量映射，改动较小。**

选 A 配置为参考，利用校准测量给每张图片一个参考服务需求 `c_k`，单位取“参考 CPU 服务秒”；配置速度因子 `a_p` 为无量纲。近似：

\[
S_{k,p}\approx \frac{c_k}{a_p}.
\]

参考配置 `a_A=1`；其他因子从校准配对测量估计。队列工作量单位也改为参考服务秒，不再把它解释成真实 MB。上传仍由独立的字节数计算。

这种映射只有在不同配置间服务时间近似可分离时成立。必须用保留图片核对误差和尾部，不能只匹配平均吞吐。如果只用 `1/平均服务时间` 替换服务率而保持统一任务常数，仍没有回答真实服务时间分布的问题。

**路线 B：逐任务、逐配置服务表，推荐用于最终实测校准证据。**

执行层直接使用配对的 `S_(k,A)`、`S_(k,B)` 和会话扰动，维护 FIFO 队列、正在执行任务的剩余服务时间与完成时间。高精度实现按事件推进上传完成、服务开始、服务结束，策略和广播仍按指定周期运行。

该路线能保留不能用单一速度比例表示的解码差异与硬件抖动。它是**执行环境的校准适配**，不是添加一个更强的 QLA 策略；所有基线使用相同执行环境。

为避免把尚未发生的随机服务时长泄漏到路由决策：

- 执行层使用实测/采样服务真值决定何时完成；
- actor 和 QL 只使用请求元数据、冻结的预期服务估计和已有陈旧反馈；
- 反馈中的等待压力采用可部署的估计，如待处理任务预测服务量之和，而不是读取未来实际抖动；
- 可行性筛选不要根据该任务未来实测服务时间选择服务器。可采用固定待处理任务数/缓存字节预算，完整记录筛选与丢弃；这与旧工作量缓冲阈值不同，需清楚定义并统一所有方法。

若路线 A 已能在保留数据上满足预先冻结的均值和尾部验收，可先完成 A；若不能，应改 B，而不是宣称常数模型已被充分校准。不要为了证明既定结论而任选更有利的路线。

### 8.3 校准后的时延和队列语义

模拟任务时延至少包括：

\[
T_k=T_k^{\rm upload}+W_k+S_{k,j}+T_k^{\rm response}.
\]

未测响应项时，可在协议中明确忽略，并说明返回结果较小这一假设；不能一面省略该项，一面称真实网络端到端实测。控制器决策开销单列；若任务需等待它，再将实际等待计入端到端时延，避免双重计数。

必须检查：新任务在上传完成前不能进入计算队列；旧任务连续执行；长上传可以跨过多个决策时隙；任务开始和完成时间与服务要求一致。现有“先服务旧队列，再接纳新任务”的时隙近似不自动等于连续时间真实服务，须做下面的验证。

建议六个执行层单元测试：

1. 一个服务器、一个任务、无排队：完成时间等于上传加服务。
2. 两任务先后上传到同一服务器：FIFO 等待与解析值一致。
3. 一个任务上传时间跨多个时隙：不能提前接纳/完成。
4. 服务过程中跨越广播和决策点：不能重复或重置服务。
5. 缓冲区满：整任务丢弃，任务计数与工作量记账一致。
6. 停止到达后 drain：所有已接纳任务完成或明确记为 unfinished，不用惩罚值伪装完成时延。

进一步用保留实测请求做单服务器串行/FIFO 重放，验证总处理时间、平均等待和 P99。若连续时间模型与现有时隙近似差异明显，报告并使用精度合格的执行层。

## 9. 时间尺度、负载和多智能体交互怎么设

### 9.1 不机械照搬 1 s 时隙和 35 个服务器

真实 ResNet 服务可能是毫秒级。若照搬统一工作量及 1 s 时隙，可能得到几乎没有排队的场景，或时隙离散误差主导尾部。因此先用独立预实验确定物理尺度，再冻结。

建议校准子实验先采用 **30 个移动用户、4 个模拟服务器、两类实测服务配置各 2 个**。它是可控共享服务子系统，不是四台实体机器；两类配置标签和服务器位置均预先固定。该实验不替代原论文的 35 服务器规模结果。

服务器位置用训练轨迹区域和固定种子产生，不根据测试结果调整。路线 B 的最小原型可先设每服务器 32 个等待任务的有限缓冲（正在执行任务另计），所有方法一致；正式阈值在预实验核对内存/等待量级后冻结。路线 A 若沿用工作量缓冲，则以参考服务秒明确阈值，两种缓冲协议不能混在同一张比较表中。

用原 KAIST 轨迹时间戳插值到新的决策网格，保留其真实时间尺度；不要直接把每个 10 s 轨迹样本当作一个 100 ms 时隙，造成未声明的运动加速。

候选决策周期 `Δ=50 ms`、广播周期 `P=100 ms`，仅作为预实验起点；若控制器实测开销、上传时间或服务时长与此不匹配，按预先规定的工程原则调整，而不是按哪组 QLA 优势更大来调整。所有时延用秒存储、图表可转换为 ms。

### 9.2 根据实测服务能力设置请求强度

计算共同图片混合下各配置的平均服务需求 `E[S_j]`，将系统处理能力粗略估计为：

\[
C_{\rm total}=\sum_j\frac{1}{\mathbb E[S_j]},\qquad
\lambda_{\rm total}=\rho C_{\rm total}.
\]

该式是负载标尺，不保证任意路由都稳定。每个节点仍需检查实际利用率 `λ_j E[S_j]`，网络与用户上传能力也会限制可实现的请求强度。

主实验建议 `ρ∈{0.60,0.85}`；另加 0.95 仅作容量敏感性。保持已有 Poisson-bursty 思想，但按物理秒生成任务率，保存实际到达率、突发概率和突发幅度。

必须做可行性检查：每用户每秒图片请求数与上传字节总量是否适合所声明的应用；若为了压满四个快速服务器需要不合理的手机拍照频率，应减少服务器、选更重的固定模型或明确称为高频视觉帧压力测试。不能把人为高频压力测试当作校园地标服务的典型业务流量。

### 9.3 反馈滞后与系统交互

在广播周期 `P` 固定时，主实验采用三个**名义检索延迟**：`{0,P,4P}`。实际 source age 仍包含距离上次广播的时间，记录真实年龄分布；`名义延迟=0` 不意味着任意决策时刻都得到当前队列。

多智能体对应明确的共享资源交互：多个用户在同一个决策周期读取共享摘要，同时输出各自 portfolio；任务上传和分配后竞争同一组 FIFO 服务器，队列影响后续请求和后续广播。不同 agent 不能只在不相互影响的独立服务器上运行。

将以下数据持久化供所有方法共享：图片 ID、到达时刻、移动位置、上传字节、资源配置、外部服务扰动块、反馈源时间戳及分类采样随机数。服务样本按“任务 ID × 资源配置 × 扰动种子”索引，不能每个策略运行时顺序抽样，导致方法改变顺序后读到不同难度的样本。

不同策略产生不同队列是结果；不同外生图片或服务扰动不是策略优势。若实机负载本身由策略触发且改变服务时间，需在实际系统实验中直接测量，不把这种内生竞争伪装成固定外生服务表。

## 10. 最小策略比较矩阵与训练安排

### 10.1 先做能回答核心问题的一组

推荐四个方法：

| 方法 | 为什么保留 |
| --- | --- |
| QLA-MAPPO Full | 最终采用的完整协调策略 |
| PPO-MV-A | 已有较强学习基线，检验收益不只是“学习胜过规则” |
| JSEQ-A | 陈旧信息/队列估计路线的比较对象 |
| score-softmax | 直接依据共享陈旧评分路由，显示共同偏好如何转化为执行集中 |

主测试：`4 方法 × 2 负载 × 3 名义延迟 × 5 配对种子 = 120 个测试 cell`，每个 cell 必须有足够完成任务以估计尾部。种子是训练及共同外生日程的配对块，不是 120 个独立设备。

为了控制训练成本：两个学习方法分别在一个预先冻结的校准训练条件上训练五个种子，例如代表性负载 `ρ=0.75`、名义延迟 `P`，然后保持 checkpoint 固定评估上述六个负载/延迟条件。共 10 个学习训练任务。JSEQ-A 如需要拟合参数，仅在共同校准/验证池拟合冻结；score-softmax 的温度等也不能在测试池选择。

这回答的是**校准环境中的固定策略反馈/负载迁移**，不是“每个测试条件重新优化之后能达到多少性能”。若以后按每个条件分别训练，要作为另一种实验明确区分，不能将两者合并解释。

建议首轮训练沿用现有 10,000 决策步作为起始共同预算，记录对应的物理时长 `10,000×Δ` 和生成请求数。checkpoint 规则、训练步数和奖励/观测归一化仅能在训练/验证阶段确认；若预实验表明预算不足，可按预先规定的规则给两个学习方法同等增加预算，再冻结最终测试。不能只延长 QLA 训练。

测试采用共同固定时长，而不是“每个方法完成 10,000 个任务就停止”。可在独立预实验后取 `H_eval=max(120 s, 10,000/λ_low)` 为起点，按最低到达率和预期接纳率预留尾部样本，再向上取整到决策周期；所有方法在同一条件使用相同起止时刻。停止到达后单独 drain，设置共同最大 drain 时长并报告 unfinished。120 s 和 10,000 是建议起点，不是当前结果或不可调整的官方标准。

### 10.2 旧 checkpoint 可否直接使用

旧 checkpoint 可以做输入维度、单位和归一化一致时的零适应诊断，但不是默认的公平正式比较。实际载荷、服务单位、服务器数量和反馈压力定义改变后，可能不兼容。

正式主结果应让学习方法在同一校准训练分布、验证规则和预算下训练；保留原算法结构，不加只对 QLA 有利的输入。若不得不调整归一化，所有方法按其适配边界同步处理，写明输入可用性。视觉 ResNet 始终冻结，不参与这一步训练。

训练预算先规定环境交互数量，同时报告物理秒数；缩小决策周期后，旧 `γ` 对应的物理折扣时间也改变。可按冻结的时间尺度规则换算折扣，例如 `γ_new=γ_old^(Δ_new/Δ_old)`，但不能声称原超参数未经改变；是否换算应在验证后统一冻结，不在最终测试中选择。

### 10.3 有余力再增加的机制闭环

依优先级增加，不是最小方案的前置要求：

1. **NoQL**：区分通用合作学习收益与 QL 路径收益。
2. **NoBias / Shuffle**：检查显式偏置与服务器动作对应关系在真实服务差异下是否仍有作用。
3. **匹配年龄的 sharedness 干预**：在同一实际反馈年龄边际下比较 `g=1` 与 `g=30`，检查共享导致的执行集中和队列变化。
4. 第二视觉模型（如固定版本 MobileNetV3 或 ResNet-50）：检验不同计算强度，而非增加更多相似图片数据集。

机制实验也必须使用同一校准执行层及配对日程。Full 对规则基线更好，不足以单独证明 QL 组件或共享奖励是原因。

## 11. 指标、统计与“收益仍存在”的判定

### 11.1 预先指定主指标

- 主效果：未截断任务完成时延的均值、P99、CVaR99；主检验突出均值和 CVaR99，P99作互补。
- 保障指标：全部生成任务的接纳率、丢弃率、unfinished、截止期限内完成比例、完成吞吐。
- 系统解释：最大实际服务器需求占比、每服务器利用率、排队时延、队列压力波动与 post-broadcast queue jump。
- 控制代价：决策计算时间、portfolio migration；与视觉服务时间分开。

时延主统计只对 accepted completed tasks 计算，但不能单独报告它而隐去丢弃/unfinished。截止期限从应用要求或预先选定的压力档设定，不能每个方法按自己的分位数选择期限。

### 11.2 保持与你论文一致的尾部定义

将 `n` 个未截断完成时延降序排列 `T_[1]≥…≥T_[n]`，采用当前论文口径：

\[
m=\max\{1,n-\lceil0.99n\rceil\},\qquad
\widehat{\mathrm{CVaR}}_{0.99}=\frac{1}{m}\sum_{r=1}^{m}T_{[r]}.
\]

正文明确这是经验最慢约 1% 的均值，避免与其他软件的分位数阈值平均法混用。每个最终测试 cell 争取至少 10,000 个完成任务，使最慢 1% 有约 100 个样本；正式测试长度按预实验统一冻结，不依结果显著性停跑。若低接纳率使尾部样本不足，如实标记并保留故障指标。

### 11.3 实际集中与队列指标如何适配

不要用“分到该服务器的 JPEG 字节占比”代替计算拥塞集中。至少报告实际任务数 share，另报告基于**参考计算工作量**的服务需求 share：

\[
L_j(t)=\sum_{k:J_k=j}c_k,\qquad
s_j^{\rm realized}(t)=\frac{L_j(t)}{\sum_\ell L_\ell(t)}.
\]

无任务时单独规定不计入或置零，并一致执行。不同服务器上的实际服务秒数若直接相加，会混入硬件速度差异；需要说明采用参考单位，或把节点 busy time/utilization 作为另一个指标。

若队列单位变为服务秒，可报告每服务器排队长度、实际等待时间，以及预测积压服务时间除以 `Δ` 的波动/跳变；若沿用论文 QOsc 形式，须重新定义对应的参考容量与单位，不能把原 MB 队列公式不加说明地套上。队列峰值减少和任务尾部改善应各有数据，不以 portfolio entropy 单独证明二者。

### 11.4 配对分析

1. 对每个固定负载与延迟，先计算每个种子的完整指标。
2. 在同一外生日程上计算 `baseline−QLA` 差值及相对改善。
3. 以种子为块，配对重采样完整的负载/延迟 profile，给出 95% CI；不要把各个任务当作独立重复用于策略显著性。
4. 硬件校准不确定性另外以测量会话为块传播；五个策略种子不能代表硬件测量误差。如果成本不足以做双层不确定性，至少对各测量会话分布做敏感性重放并单列。
5. 五种子区间可能较宽；报告效应量和全部点，不把 CI 跨零称为“证明没有影响”。

结论判定：

- 如果相同校准负载下，平均与尾部改善方向稳定，且没有靠更多丢弃/unfinished 获利，可支持“协调收益在实测校准服务条件下仍存在”。
- 如果仅平均改善、尾部无清晰改善，只保留平均收益，不声称控制极端延迟。
- 如果集中/queue jump 下降而尾部不变，支持相应队列机制，不自动推出服务质量全面改善。
- 若收益仅在某一资源配置/负载出现，报告条件性收益；不要扩大到所有 edge-AI 服务。
- 若公平校准后收益消失或变差，应检查原因并如实报告，不能通过测试集挑选或删除不利资源配置维持旧叙述。

## 13. 可选小型实际请求实验：增强 DAC 系统证据

在校准模拟跑通后，可用两个推理服务进程做一个小型实际请求实验，验证“队列 + 延迟摘要 + 同步用户响应”的实现。它不是完整校园部署，也不是最小方案必需。

建议步骤：

1. 客户端生成多个逻辑用户请求和共同图片日程；周期读取服务状态摘要。
2. 两个 FIFO 服务进程部署同一 ResNet，设置不同且互不重叠的 CPU 资源集合，模型常驻。
3. 独立核对同时运行时的资源隔离及服务分布。单进程独占测量不能直接代表并行进程的服务能力。
4. 控制器按周期路由；各方法用同样请求、缓存预算和陈旧摘要规则。
5. 开环按既定到达时间发请求，不因前一个响应慢而自动降低下一请求率，避免漏记拥塞时的等待。
6. 逐请求记录实际上传、排队和响应；用户生成器本身不能饱和，否则测到的是生成器瓶颈。

同一主机的两个服务进程只能称“资源隔离的单机服务原型”。实际网络若为 localhost 或有线 LAN，应直接写明；人工延迟和带宽控制不等于校园无线部署。客户端与服务器分机时保留同钟计时原则。

这项实验的价值在于验证执行闭环，而不是把逻辑用户数量写成实体手机数量。

## 14. 顺序、停止点与工作量控制

| 阶段 | 具体工作 | 进入下一阶段的条件 |
| --- | --- | --- |
| 0：冻结预案 | 选择主模型、图片编码、资源配置、指标和采样清单 | 配置文件/清单可追踪 |
| 1：独立预实验 | 少量图片，检查计时、单位、资源速度和合理请求强度 | 流水线正确，非实验结果导向选条件 |
| 2：正式测量 | A/B 配对、分块、预热、完整记录 | 计时数足够，错误及环境漂移有记录 |
| 3：独立校准 | 路线 A 验收；不适用则路线 B，验证队列执行 | 保留数据误差与执行单测通过 |
| 4：共同训练与冻结 | 同训练/验证日程、输入边界、归一化和 checkpoint 规则 | 测试之前配置及权重冻结 |
| 5：120-cell 评估 | 两负载、三延迟、五配对种子、四方法 | 完整任务日志、故障率与尾部样本审计通过 |
| 6：统计与解释 | 种子块配对、测量会话敏感性、结果图和边界 | 每个论文 claim 均有对应数据 |

不要在第一阶段就增加第二视觉模型、量化、动态批处理、35 台实体部署或完整 GLDv2 训练。先完成真实 JPEG → 服务测量 → 保留校准验收 → 配对策略比较这一条闭环。

## 15. 论文中最终能说什么，不能说什么

若实验支持，可以写：

> We evaluate QLA-MAPPO in a simulation calibrated with measured JPEG payloads and per-request ResNet-18 service times under two CPU resource configurations. The results test whether cooperative offloading benefits persist when communication and computation demands are grounded in real inference measurements.

有了结果后，再按实际效应补充具体结论；上述文字本身不预设 QLA 更优。

不能仅凭这项最小实验写：

- “在 35 台真实校园边缘服务器上验证”；
- “端到端无线时延已实测”，如果网络仍模拟；
- “验证了校园建筑识别准确率”，如果只是 ImageNet 分类；
- “服务时间由图像大小决定”，如果只是相关或仅解码阶段相关；
- “实现对任意设备/模型的迁移”，如果只测一 CPU、两线程配置；
- “证明直接优化 CVaR”，如果仍使用现有 bounded reward proxy。

这项补充最直接提高的是**工作负载和计算服务假设的外部可信度**，并不能单独证明部署泛化、控制理论保证或所有组件的因果贡献。它不要求在论文中叙述旧版与新版算法更新史。

## 16. 执行前检查清单

- [ ] 图片和模型来源、版本、许可、哈希均记录。
- [ ] 原始 JPEG 载荷与模型张量大小分开。
- [ ] 统一 FP32、batch 1、预处理和输出质量。
- [ ] 服务计时含解码/预处理/推理/后处理，不含队列和模型加载。
- [ ] 预热剔除，GPU 如使用则完成同步，日志不在计时区间。
- [ ] 两资源配置的测量顺序分块随机，逐会话环境状态记录。
- [ ] 图片池与测量会话角色区分，最终测试不用于校准/选参。
- [ ] 上传字节、计算需求、服务率和队列单位一致；旧 MiB 换算已核对。
- [ ] 请求摘要、QL 预测、基线适配和可行性筛选同步接入新任务属性。
- [ ] 隐藏实际未来服务抖动，不向 actor 或路由筛选泄漏。
- [ ] 真实时间尺度、移动轨迹时间戳、广播时间与实际 source age 一致。
- [ ] 所有方法使用同一持久化任务/服务/反馈日程。
- [ ] 未截断尾部与丢弃/unfinished 同时报告。
- [ ] 配对单位是种子，会话不确定性另列，不把任务数当独立实验重复。

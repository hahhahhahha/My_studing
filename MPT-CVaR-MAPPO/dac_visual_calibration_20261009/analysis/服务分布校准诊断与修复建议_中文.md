# 服务分布校准：原因诊断与修复建议

日期：2026-10-10。本文为已观测失败后的探索性诊断与新方案建议，不是重新测量或验收通过报告。没有修改冻结源码、原始测量、划分、阈值、权重、论文或旧强化学习结果，也没有启动新进程。

## 1. 结论先行

当前最有证据支持的修复方向是：**补足尾部图片覆盖，并改用保持输入尺寸/上传字节与服务时间关系的条件经验分布**，而不是重新安装PyTorch、修GPU或放宽P99阈值。

现有计时入口使用官方预训练权重、FP32、batch=1、eval/inference_mode；CPU-1T和CPU-4T固定线程数与不同物理核的亲和性，分块预热并保留慢请求。未发现足以解释本次39.18%差异的明显计时边界或单位错误，但本次只读检查不是对所有运行时干扰的完整排除。

## 2. 直接数据证据

| 比较项 | 校准池 | 验证池 | 含义 |
|---|---:|---:|---|
| 独立图片数 | 2000 | 500 | 重复5次/3次不增加独立图片种类 |
| 超过100万像素的图片 | 46（2.30%） | 2（0.40%） | 输入尺寸尾部明显不平衡 |
| 超过200万像素的图片 | 16（0.80%） | 0 | 验证池完全未覆盖这一尺寸层 |
| 图片像素数P99 | 1920000 | 602112 | 两池的输入尾部不同 |
| CPU-4T总服务时间P99 | 29.6038 ms | 21.2702 ms | 原门控未通过，误差39.18% |
| CPU-4T纯推理阶段P99 | 16.3524 ms | 16.2385 ms | 相对差约0.70%，差异远小于完整服务时间 |

校准CPU-4T中，服务时间大于等于其P99的101条记录里有62条来自超过200万像素的大图，占61.39%。这些最慢记录的总耗时合计中，解码与预处理占62.76%。12张图片在5个会话中每次都进入这一尾部集合；这些重复出现的大图慢请求不宜当成可随意剔除的偶发异常。

四线程校准5个会话的P99为28.0920、32.0911、28.1878、29.6260、31.4709 ms；验证3个会话为27.6550、18.9279、19.0093 ms。验证长尾也存在会话变化，因此不能把尺寸不平衡解释为全部差异的唯一已证明原因。当前没有连续温度、频率或线程调度追踪，尚不能断言操作系统、热状态或背景负载的具体因果。

相关原始统计及证据SHA256见`SERVICE_DISTRIBUTION_DIAGNOSTIC_20261010.json`。纯推理P99不是总服务P99，不能把前者替换后者来使原门控通过，也不能把各阶段的P99直接相加。

## 3. 为什么目前的校准方式容易失败

原服务分布验收直接比较两池混合后的均值/P95/P99，而抽样只平衡了类别，没有保证像素数和JPEG大小尾部的覆盖。对含原JPEG解码的服务，图片输入分布不同会改变服务时间分布。

ResNet-18官方IMAGENET1K_V1预处理最终裁剪到224×224，但仍需先处理原JPEG。固定的网络输入尺寸并不消除原图解码和缩放成本。官方说明：[Torchvision ResNet-18](https://docs.pytorch.org/vision/stable/models/generated/torchvision.models.resnet18.html)。

一线程的网络计算底数更大，四线程降低了推理时间后，解码与预处理更容易影响总服务时间的相对长尾。该解释与上述阶段统计相容，但不等于已经完成所有因素的因果隔离。

不能把两池完整服务P99的差异全部归结为模型不准：首先需要定义所预测的请求人口，并比较该人口下的预测与实测，而不是要求不同输入混合比例的两个无条件分布天然一致。

## 4. 推荐修复步骤（尚未执行）

### 第一步：保留原失败运行，单独登记新方案

- 原23000条正式记录及失败报告保持不变，不能覆盖或把`accepted=false`改成`true`。
- 原500张验证图片已经用于本次诊断，可以归为开发/诊断数据；若据此改变模型或设计，就不能再把这一组当成未见的确认性验证。
- 原冻结测试池继续不访问计时结果、不用于选模型或阈值。采用独立V2目录/协议记录新方案，正式测量之前冻结设计、随机种子、输入指纹、模型与验收标准。

### 第二步：让新验证覆盖输入尺寸尾部

- 按类别及少量尺寸层分层抽样；JPEG字节数作为额外的分布平衡检查或条件特征，不宜把两个连续特征交叉成大量稀疏小格。
- 可采用像素层`≤0.25MP`、`0.25–0.5MP`、`0.5–1MP`、`1–2MP`、`>2MP`作为候选。它们是失败后提出的新设计，须在新的确认测量前固定，不能声称它们属于原事前方案。
- 初步建议新验证约2000张不同图片，而不是将原500张多计几遍；具体数量和每层配额须先结合可用图片、稀有层容量与目标分位数的不确定性确定。2000张不是保证通过或已经完成样本量论证。
- 只读库存检查显示还有6869张未使用的官方train图片，其中45张超过2MP、111张超过1MP；这只是库存，仍需精确/近重复检查和类别/尺寸层可行性检查，才可确认新划分。
- 稀有层可增加测量覆盖，但若过采样，必须按事先定义的目标请求分布加权汇总，不能把过采样后的比例当成自然工作负载比例。不能只挑选让新P99靠近旧P99的图片。

### 第三步：把无条件混合表改为条件经验模型

建议描述的是`服务时间 | CPU配置、图片像素数、JPEG字节数`，而非每个CPU配置只有一条适用于所有图片的统一服务分布。

- 现有校准数据仍可用于候选模型开发，不必因验收失败全部作废。
- 优先使用简单、可解释的尺寸分层经验表；保留同一请求的JPEG字节、像素数、CPU-1T/4T配对耗时及阶段耗时，不能独立抽样上传量、各计时阶段或两个配置后破坏相关性。
- 细化条件特征或模型拟合只使用开发/校准数据；模型结构、分层/平滑/稀疏层处理和参数在新验证服务计时揭晓之前冻结。
- 验证时，用新请求池已知的尺寸/字节分布生成预测服务分布，再与这一池的实测服务分布比较。条件输入可以使用，验证服务耗时不能用于调参后又宣称同一次确认性通过。
- 若样本对某尺寸层没有支持，应明确标为不支持/需补测，而非凭空外推或静默回退为低耗时。

### 第四步：减少会话与数据角色的混淆

- 原来先完成所有校准会话，再完成所有验证会话，数据角色与测量时间段关联；新确认方案应把校准/参考块与新验证块放在同一会话中随机交错顺序，CPU配置保持配对和反平衡，不并发计时。
- 同一组参考图片可用于观察会话漂移；应预先规定其作用，不根据最终延迟临时选择删会话或归一化。
- 保留现有预热、物理核亲和性、独立进程与固定线程配置。增加只读的后台活动/CPU状态记录可辅助诊断，但不能改成用块平均时间代替单请求长尾。
- 未来若想证明跨日重复性，应明确安排多日；不能把单日多会话当作跨日或多设备证据。

PyTorch官方基准指南也强调线程数、预热等计时控制：[PyTorch Benchmark](https://docs.pytorch.org/tutorials/recipes/recipes/benchmark.html)。其批量平均计时适合辅助检查计算内核，不应直接代替本实验的逐请求服务P99。

### 第五步：独立复验后再进入测试

- 首选继续沿用原均值10%、P95 15%、P99 20%的工程容差；修改的是候选建模和采样设计，不是为通过而放宽数值。
- 使用完全冻结的新规则评估新验证池：既报告点估计误差，也按图片和会话层级检查不确定性，避免把重复计时当成独立图片。
- 只有新方案的既定验收通过，才运行保留测试和校准后的模拟器比较。若再次失败，归档并分析，不反复补测直到结果变好。
- 服务分布通过不代表模拟器队列/排队模型或QLA收益通过；FIFO、队列守恒、网络计时口径和策略比较仍需各自验证。

## 5. 不建议的“修复”

- 放宽P99上限、删除大图或慢请求、只保留中位数、忽略解码/预处理、只测纯推理：都会改变原科学问题或掩盖失败。
- 仅切换GPU、升级包或重新初始化：当前目标是CPU1T/4T真实服务，且主要可见差异与输入尺寸有关，暂无依据把这些作为首要修复。
- 将原上传JPEG提前缩小以降低长尾：可以作为真实客户端压缩方案的另一项研究，但会改变上传量、视觉质量和计时位置，不是原条件下的校准修复。若应用确实采用它，必须定义请求格式并重新测量质量与完整成本。
- 用测试池拟合经验表，或挑一个更接近校准P99的子集：破坏测试独立性。
